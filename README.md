# Inkline

System-wide, **on-device** predictive-text autocomplete for macOS (and later
Windows). As you type in any app, Inkline predicts the rest of your sentence and
shows it as gray inline "ghost text" at the caret; press <kbd>Tab</kbd> to accept
word by word, or keep typing to ignore. All inference runs locally via
`llama.cpp` — nothing you type ever leaves the machine. No telemetry.

> **Status:** Phases 1–4 complete and runnable. Typing in any AX-friendly app
> (TextEdit, native Cocoa apps, Safari) shows real ghost-text completions from a
> local `llama.cpp` model at the caret; word-by-word accept works. Ships with a
> menu-bar app, a settings window (global / per-app / secure-field toggles), and
> in-app **model management** (list, switch, download a `.gguf` by URL). The Rust
> core spawns and manages a `llama-server` subprocess and talks to it over
> localhost HTTP.

## Architecture

A shared **Rust core** ("the brain") compiled to a C-ABI library, plus thin
**native shells** per platform that own all OS-specific I/O. A second shared
element is the settings/model UI — one cross-platform web file
(`ui/settings.html`) hosted in each shell's WebView.

```
┌──────────────────────────────┐        ┌──────────────────────────────┐
│  Native shell (per platform) │        │  Rust core  (cdylib, C-ABI)  │
│                              │        │                              │
│  macOS: Swift                │  call  │  • debounce / timing         │
│   • AXUIElement text read    │ ─────▶ │  • prompt building (few-shot)│
│   • CGEventTap keystrokes    │ on_ctx │  • output sanitize / overlap │
│   • ghost-text NSPanel       │        │  • llama-server subprocess   │
│   • menu bar, permissions    │ ◀───── │  • HTTP completion client    │
│   • settings + model files   │ callbk │  • model loading             │
│  Windows (later): C#         │        │                              │
└──────────────────────────────┘        └──────────────────────────────┘
         │                                          ▲
         │  hosts shared ui/settings.html in a WebView (JS↔native bridge)
         └──────────────────────────────────────────┘
```

**Division of labor:**

- **Rust core** owns everything that is *not* an OS call: debounce, prompt
  building, output sanitizing / suffix-overlap filtering, the `llama-server`
  subprocess lifecycle + HTTP client, and model *loading*. It **never** makes OS
  UI/accessibility calls.
- **Native shells** own *all* OS-specific I/O: accessibility text + caret reads,
  keystroke interception, text injection, the ghost overlay, menu-bar/tray, the
  permission flows, settings persistence, and model *file* management.
- **Shared UI** (`ui/settings.html`) — the settings + model-management interface
  is one cross-platform HTML/CSS/JS file, hosted in each shell's WebView (macOS
  `WKWebView` now, Windows WebView2 later) over a small JS↔native message bridge.
  Don't fork it.

> The original design put settings + model management in the core. In practice
> those decisions are OS-flavored (which app is focused, is the field secure,
> native file download), so they currently live shell-side; moving the
> schema/persistence into the core behind FFI is a deferred "Stage 2." See
> `HANDOFF.md §7a`.

**FFI boundary** — narrow and dumb:

- Events flow **in** as simple calls (`inkline_on_context`).
- Suggestions flow **out** via a registered C callback function pointer — no
  async/await crosses the boundary.
- Each context carries a **sequence id** (`seq`) that rides the round-trip, so
  the shell can drop a suggestion the user has already typed past.
- Strings are UTF-8 `char*` with explicit ownership: the core allocates strings
  handed to the callback; the shell releases them with `inkline_free_string`.
- The C header (`core/include/inkline.h`) is generated by **cbindgen** at build
  time (`core/build.rs`).

**Inference** — a `llama-server` process runs as a child on an ephemeral
localhost port; the core health-checks it, talks HTTP (`/completion`), restarts
on crash, and switches models by restarting with a new `-m`. A dedicated manager
thread owns the child; `complete()` is lock-free. Every request is a plain
`/completion` — the prompt builder (`prompt.rs`) uses **few-shot** prompting
gated on caret position to get short, suffix-aware completions out of a *base*
model, the output is run through a **sanitizer** (`inference.rs`) and a
**suffix-overlap guard** (`overlap.rs`), and **logit_bias** suppresses control
tokens for the common instruct families. See `HANDOFF.md §8`–`§8a` for the why.

## FFI surface

```c
typedef void (*SuggestionCallback)(const char *suggestion, uint64_t seq);

void inkline_init(SuggestionCallback callback);   // register callback, start worker
void inkline_on_context(const char *text, uintptr_t cursor_pos, uint64_t seq);
                                                  // full field text + caret BYTE offset + seq id
void inkline_set_model(const char *path);         // load a GGUF (async); switch to real inference
void inkline_free_string(char *ptr);              // free a string from the callback
void inkline_shutdown(void);                      // stop the worker + reap llama-server
```

`inkline_on_context` takes the **full field text** and the caret as a **UTF-8
byte offset**; the core splits it into prefix/suffix at a char boundary. The
`seq` id is stamped per context and echoed on the callback so the shell can drop
stale suggestions.

## Prerequisites

- macOS (Apple Silicon or Intel) with the Xcode command-line tools / Swift 6+.
- Rust toolchain (`rustup` / `cargo`) and `cbindgen` (`cargo install cbindgen` —
  only needed if you build the core directly; it is otherwise pulled in as a
  build-dependency).
- **`llama-server`** on the system (e.g. `brew install llama.cpp`). The core
  finds it via `$INKLINE_LLAMA_SERVER`, then `/opt/homebrew/bin`,
  `/usr/local/bin`, then `PATH`.
- **A GGUF model.** Development is on the **base** `gemma-4-E2B.Q6_K.gguf` — the
  few-shot prompts are tuned for it, and an A/B confirmed base + few-shot beats
  the instruct sibling (see `HANDOFF.md §8a`). You can also download a model
  in-app (menu bar ✎ → Settings… → paste a `.gguf` URL). `run.sh` picks the
  first `*.gguf` in `models/` as the dev override; pin one with
  `INKLINE_MODEL=models/gemma-4-E2B.Q6_K.gguf`.

## Build & run

```bash
./scripts/setup-signing.sh   # one-time per machine: create the "Inkline Dev" cert
./run.sh                     # build, assemble & sign Inkline.app, and launch it
./run.sh --build             # build + assemble the bundle only (don't launch)
```

`run.sh` builds the Rust core (release), regenerates and syncs the C header into
the Swift module, fixes the dylib install name to `@rpath`-relative, builds the
Swift executable, assembles `mac/build/Inkline.app` (copying the dylib into
`Contents/Frameworks` and `ui/settings.html` into `Contents/Resources`, with an
rpath pointing at the framework), **code-signs the bundle with the "Inkline Dev"
identity** (falling back to ad-hoc with a warning if the cert is missing), and
launches it. It also writes the chosen dev model path into the app's
`UserDefaults` (`InklineModelPath`); the app reads it on launch and passes it to
`inkline_set_model`, which spawns `llama-server` against that model.

> **Why the signing cert matters:** a stable code-signing identity keeps the
> Accessibility permission across rebuilds. Ad-hoc signatures change hash every
> build, so macOS drops the permission each time. `setup-signing.sh` creates a
> self-signed `"Inkline Dev"` identity once (idempotent; may prompt for your
> login password to trust it).

**First run:** macOS will ask you to grant **Accessibility** permission
(System Settings → Privacy & Security → Accessibility). The app's menu-bar icon
shows `✎⚠` until permission is granted, then `✎`. The event tap and AX reads
can't run without it.

**Try it:** with permission granted, open **TextEdit**, switch to plain text
(Format → Make Plain Text), and start typing a sentence. After a brief pause
(and a few seconds on first launch while the model loads), gray ghost text with
the model's predicted continuation appears at the caret.

### Keybindings (while ghost text is shown)

- <kbd>Tab</kbd> — accept the **next word** (completing the current word if the
  caret is mid-word); keep pressing to walk through the suggestion word by word.
- <kbd>`</kbd> (backtick, no Shift) — accept the **whole** remaining suggestion.
  While a suggestion is visible the backtick is consumed (you won't get a literal
  `` ` ``); press <kbd>Esc</kbd> first if you need to type one.
- <kbd>Esc</kbd> — dismiss. Any other key dismisses and triggers a fresh
  prediction.

> Until a model finishes loading (or if no model is set), the core falls back to
> a canned **stub** generator so the UI still demonstrates the typing loop.

### Settings & model management

Open from the menu bar: **✎ → Settings…** (or use the quick **Enable Inkline**
toggle). The window is the shared `ui/settings.html` hosted in a `WKWebView`:

- **Toggles** — global on/off, "skip password fields", and **per-app**
  enable/disable. These gate whether the shell even asks for a suggestion.
- **Models** — list installed models, switch the active one, **download a
  `.gguf` by URL** (with progress + cancel), and **choose the models folder**.
  Default folder: `~/Library/Application Support/Inkline/models/`.

### App coverage

Where Inkline can place ghost text depends on what each app exposes through
Accessibility — reading text is easy, but anchoring the ghost needs caret
geometry, which is the hard part.

- **Native Cocoa apps** ✅ (exact caret bounds).
- **Safari** ✅ on AX-friendly sites (exact) and font-exposing sites (estimated).
- **Chrome / Electron** — text reads (via the `AXManualAccessibility` unlock) but
  Chromium exposes no caret bounds or font, so **no ghost is shown there yet**.
- **Google Docs / canvas editors** ✗ — same limitation.

Precise placement in Chrome and web editors needs an OCR caret finder
(screenshot + Vision) — a planned, self-contained project. See `HANDOFF.md §7b`.

### Debugging / logs

```bash
log stream --predicate 'process == "Inkline"' --level info
defaults write com.inkline.app InklineDebug -bool YES   # logs caret/overlay geometry
defaults delete com.inkline.app InklineDebug            # turn off
```

`run.sh` launches via `open`, so env vars don't reach the app — use the
`InklineDebug` UserDefault, not `INKLINE_DEBUG`, when launched that way.

## Testing

```bash
cargo test -p inkline-core    # ~20 unit tests: sanitizer, prompt shapes, overlap, request build
```

The pure text logic is unit-tested; the HTTP/subprocess paths are verified
manually against a live `llama-server`. Prompt quality (over-generation,
suffix-awareness, mid-word behavior) is model-specific and only observable live,
so re-verify against the server when changing prompt or inference behavior — and
re-check the few-shot example strings if you swap models. See `HANDOFF.md §12`.

## Roadmap

- **Phase 1 ✅** — the FFI spine (Rust core + cbindgen + Swift round-trip, stub).
- **Phase 2 ✅** — the typing loop: Accessibility permission, `CGEventTap`,
  `AXUIElement` text/caret reading, ghost-text overlay, accept/dismiss.
- **Phase 3 ✅** — real local inference: `llama-server` subprocess manager, HTTP
  completion client, `inkline_set_model(path)`, plus the prompt builder,
  output sanitizer, suffix-overlap guard, and multi-model logit_bias.
- **Phase 4 ✅** — app shell: settings WebView (global / per-app / secure
  toggles) and model management (list, switch, download-by-URL), with the UI as a
  shared `ui/settings.html`; broader app coverage (native + Safari) with correct
  font sizing.
- **Later** — OCR caret finder (unlocks Chrome + web editors), personalization /
  writing instructions, model-management follow-ups (verified catalog,
  delete/resume), code-signing + notarization, and the Windows C# shell reusing
  the same core and shared UI.

## Privacy

No network calls except to the local `llama-server` (and model downloads you
explicitly start). No telemetry. Nothing you type leaves your machine.
